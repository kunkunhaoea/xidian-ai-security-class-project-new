# 个人科研工作台总体设计

本文用于团队理解整体目标、划分职责和开展适配。当前已建立目录与说明，统一启动、网页集成和跨项目共享能力尚待实现。

## 1. 建设目标

将四个独立项目连接为一个个人写论文的工作台：一键启动，通过统一入口使用各项目，以共享课题资料衔接研究过程。

用户负责筛选资料、判断结论和决定下一步，AI协助阅读、讨论、构思、实验和写作。各阶段可以多轮修改、反复往返，不要求输入一个方向后自动完成整篇论文。

系统面向单人本地使用，团队共同开发代码，各自维护研究资料。优先复用原项目及网页，允许为共同目标进行必要适配。

## 2. 总体框架

整体由统一入口、项目适配、四个原项目和共享课题资料组成。

```text
用户通过统一工作台选择课题、配置服务和启动操作
                         │
                    项目适配层
                         │
          ┌──────────┬──────────┬──────────┐
        项目04      项目03     项目01     项目02
        资料采集    阅读问答   科研引擎   科研引擎
          └──────────┴──────────┴──────────┘
                         │
               shared：按课题隔离的资料与成果
                         │
                Obsidian / VS Code 阅读编辑
```

图中表示职责关系，不限定实际调用协议。四个项目不需要互相直接调用，通过适配层访问共同资料和保存成果即可形成协作。

| 部分 | 职责 |
| --- | --- |
| workbench | 统一入口、项目配置、启动管理、状态与结果入口；优先复用已有网页 |
| adapters | 衔接课题资料与原项目输入输出，协调项目调用和成果归档 |
| projects | 保留四项目能力与独立运行环境，按目标进行必要修改 |
| shared | 存放个人课题资料、研究文档和实验成果，供项目与用户共同使用 |
| docs | 维护总体设计、开发日志及组会材料，支持团队协作 |

## 3. 研究过程与项目定位

典型过程为：采集资料 → 人工筛选阅读 → 文献问答和笔记 → 讨论创新点 → 编辑实验方案 → 人工确认执行 → 分析结果与写作。用户可以返回任意阶段补充资料或修改研究方向。

| 项目 | 原有主要能力 | 在工作台中的定位 |
| --- | --- | --- |
| 04 Intelligence Gathering | 多源检索、采集、分析和归档 | 外部研究资料入口 |
| 03 DeepTutor | 文档理解、知识库问答、讨论与内容生成 | 阅读与研究讨论助手 |
| 01 AI-Researcher | 基于想法、论文和参考代码开展调研、实现、实验与写作 | 可选科研引擎 |
| 02 AI-Scientist-v2 | 想法生成、实验搜索与迭代、结果汇总和论文生成 | 可选科研引擎 |

01不限定为论文复现，02不限定为实验设计。二者能力重叠，用户按需要选择，不要求先01再02，也不强制将研究阶段分配给某一个项目。

## 4. 共享资料原则

- 共享目录固定为仓库根目录的shared/，不同课题独立存放。
- shared保存论文、笔记、创新点、方案、实验代码与结果、论文草稿等需要交接的内容。
- 每次任务默认不选择资料，由用户指定本次使用的文件；不默认读取整个课题。
- 用户在Obsidian或VS Code中阅读、编辑，项目使用选定资料并将成果写回对应课题。
- 研究笔记由用户主动保存，保留生成时间、参考文件和对应对话片段，区分人工结论、AI建议与论文证据。
- 实验方案可编辑，经用户确认后执行；保留执行时的方案与输入，使结果可追溯。
- 用户授权后允许AI修改文件，避免覆盖历史实验结果。

shared是共同文件来源，不要求四项目共用同一数据库。内部索引、缓存和必要运行数据可保留在原项目中，但对用户选定资料的修改应有明确的更新途径。

inputs.yaml作为任务资料选择的记录约定，由适配层衔接原项目，不是四项目已有的通用功能。具体字段、文件转换和内部实现由后续开发确定，不在本总体设计中展开。

## 5. 仓库与协作边界

```text
仓库根目录/
├── COURSE.md                 课程说明与提交规范
├── projects/                 四个现有项目
├── workbench/                统一入口与服务管理
├── adapters/                 项目适配
├── shared/                   个人课题资料，Git忽略
│   └── topics/               各课题独立目录
└── docs/
    ├── workbench-design.md    总体设计
    ├── devlog/               开发日志
    └── meetings/             组会文档与PPT
```

Git同步源码、适配代码和团队文档；shared、密钥、个人运行状态和Codex本地文件不提交。选定的研究进展整理为组会材料后，可放入docs/meetings同步。

## 6. 团队分工原则

| 负责部分 | 对整体交付的责任 |
| --- | --- |
| 公共集成 | 维护共同约定、统一入口与启动，组织模块联调 |
| 项目04 | 采集资料进入正确课题，来源和附件状态清楚，后续模块能够使用 |
| 项目03 | 使用选定资料进行阅读问答，保存可继续编辑的研究笔记 |
| 项目01 | 基于选定资料开展科研操作，将相关成果保存到课题 |
| 项目02 | 基于选定想法与方案开展实验和写作，保存可追溯成果 |

各负责人自行确定必要的配置、输入输出转换、提示词和流程修改。共同要求是：选定资料被实际使用，成果能够交接，课题之间不会串用。公共约定的变化需同步设计并通知相关成员。

开发日志记录工作、验证结果和待解决问题；组会材料记录个人研究进展。提交方式参见[COURSE.md](../COURSE.md)。

## 7. 实施顺序与完成标准

先确定共享资料约定并完成各项目读写适配，再联调一次真实研究过程，随后完成一键启动和基础网页集成。

完成后应达到：

- 一键启动后能访问各项目和必要操作入口。
- 用户能按课题选择资料、讨论和修改，并明确决定是否执行实验。
- 论文、笔记、方案和实验成果能够跨项目使用。
- 至少完成一次真实API实验，结果与实际输入、方案相对应。
- 关闭浏览器后后台任务继续，重新打开能查看状态和结果。

不将独立知识服务、全自动阶段编排、多用户系统、Git同步研究资料或全面重写网页列为第一版要求。具体技术方案随适配验证逐步补充。
